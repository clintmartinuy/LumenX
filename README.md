# LumenX PH

Product catalog, booking, Messenger auto-reply, and ops console for LumenX PH. See
[`LUMENX-SPEC.md`](../LUMENX-SPEC.md) for the full spec this is built against.

**Status:** Phase 1 (Foundation) complete — scaffold, full schema + RLS, seed data, auth,
and `lib/money.ts`. Phases 2–9 (public site, inventory, POS, booking, inquiries/auto-reply,
Messenger, finance, polish) are not built yet.

## Setup

1. `pnpm install`
2. Create a Supabase project, then copy `.env.example` to `.env.local` and fill in the
   values (each has a comment on where to find it). A placeholder `.env.local` is already
   present so `pnpm dev` runs without a real project, but auth and any database access will
   fail until you connect one.
3. Apply the migrations, in order, against your project — either:
   - `supabase link` then `supabase db push` (recommended), or
   - paste each file in `supabase/migrations/` into the Supabase SQL editor in filename order.
4. Run `supabase/seed.sql` the same way (SQL editor, or `supabase db reset` if using the
   Supabase CLI locally with Docker).
5. Create your first staff account — **not** done by seed.sql, see below.
6. `pnpm dev`.

### Bootstrapping the first staff account

`seed.sql` deliberately does not insert into `auth.users` — doing that outside Supabase's
Auth API is a known way to end up with accounts that can't actually log in (missing
`auth.identities` rows, wrong password-hash version, etc.), and it isn't portable to a
hosted project's SQL editor. Instead:

1. In the Supabase dashboard: Authentication → Users → Add user (or use the CLI/API),
   create an account with a real email and password.
2. Copy that user's UUID, then run in the SQL editor:
   ```sql
   insert into staff_profiles (user_id, full_name, role)
   values ('<uuid-from-step-1>', 'Your Name', 'owner');
   ```
3. Log in at `/login` with that email/password.

## Architecture notes

- **Money** is stored as integer centavos (`bigint`) everywhere and only ever touched
  through `lib/money.ts`. Nothing else should format or parse currency.
- **`product_stock`** (quantity on hand + moving-average cost per product) is a plain
  Postgres view, not a maintained table — it replays `stock_movements` chronologically via
  a recursive CTE. This was the explicit trade-off called out in the spec (§5.2): a view
  can't drift from the source data, at the cost of recomputing on every read. Revisit as a
  maintained table only if this proves measurably slow. `product_stock_status` is a
  public-safe projection (badge only, never the raw quantity) that anon can read directly.
- **Public-facing writes** (contact form, booking wizard, chat widget, Messenger webhook)
  will go through Server Actions/Route Handlers using the service-role client
  (`lib/supabase/admin.ts`), not direct anon table access — there's no anon RLS policy for
  `customers`/`inquiries`/`bookings` by design, since there are no customer accounts (spec
  non-goal). Zod validation at those boundaries is the security control, not RLS, for that
  specific path.
- **Reference numbers** (`PO-YYYYMM-####`, `INQ-YYYYMMDD-####`, `BK-YYYYMMDD-####`,
  `S-YYYYMMDD-####`) are generated by a `next_reference()` Postgres function backed by a
  `reference_counters` table, wired up as column defaults — not generated in application code.

## Assumptions flagged for the owner (spec §16, plus two found during the build)

The six assumptions listed in spec §16 (single location, 0% tax default, moving weighted
average costing, fixed-equity profit split with no salaries, per-line warranty with manual
RMA, single-technician booking slots) all still apply as documented in the spec.

Two additional judgment calls made while writing the schema/RLS, worth confirming:

1. **Partner data read access.** Spec §9's role matrix describes `admin` as having
   "everything except finalizing distributions and editing equity" (implying broad partner
   visibility), while §9.9 labels the entire `/admin/partners` section "Owner-only." These
   are in tension. Implemented as: **admin+ can read** all partner tables (contributions,
   distributions, payouts), but **only owner can write** anything (equity, contributions,
   distributions, payouts). See `supabase/migrations/00008_partners.sql`.
2. **Cost/margin visibility for plain `staff` vs `admin+`.** Spec §9 says staff gets
   "inventory read + adjustments... no cost prices, no margins." Postgres RLS is row-level,
   and staff/admin share the same `authenticated` Postgres role (there's no per-app-role
   column privilege split available), so hiding specific columns (`unit_cost`, `cogs_total`,
   `average_unit_cost`, `gross_profit`) from `staff` while still showing the row can't be
   done at the RLS layer. `suppliers`, `purchase_orders`, `purchase_order_items`, and
   `expenses` are restricted to admin+ entirely (they're cost-heavy tables end to end).
   `stock_movements`, `product_stock`, `sales`, and `sale_items` are staff-readable at the
   database level; hiding their cost/margin columns from plain `staff` specifically needs to
   happen in the admin UI's query layer (explicit column selection per role) when those
   pages get built in Phase 3/4/8/9 — flagging now so it isn't missed later.
